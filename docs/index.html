Project overview

Train models larger than your GPU, over the PCIe bus you already have.

TrainStream is a standalone C++/CUDA extension for PyTorch. It moves optimizer state, gradients and activations into pinned host RAM, streams them over dedicated CUDA copy streams, and overlaps all of it with compute. It uses no DeepSpeed, no bitsandbytes and no third-party libraries: only the C++ standard library, the CUDA runtime and PyTorch's ATen.

Overview

Memory architecture

TrainStream manages three independent data paths. Each runs on its own CUDA stream and is ordered against compute with CUDA events, never with a device-wide sync. A fourth actor, a pool of C++ worker threads, runs the optimizer math on the host.

Duplex factor 1.0: the two directions share one budget here

On this Windows laptop, pushing H2D and D2H at the same time yields the same 27.9 GB/s as one direction alone, so the copy engines effectively serialise. Workstation and Linux systems usually measure close to 2×. TrainStream's offload model reads the measured factor rather than assuming one, which is why it pages fewer activation blocks here than the raw bandwidth suggests.

Bytes per step, worked through

For cpu-mode AdamW on N fp32 parameters, each step moves 4N bytes down (gradients) and 4N bytes up (updated weights). For the 1.8B model that is 7.3 GB each way: about 265 ms per direction at 27.4 GB/s, or about 530 ms when the directions serialise. The backward pass of that model at batch 8 × 512 tokens takes about 460 ms, so the link is roughly saturated before a single activation is paged. That is exactly the situation the profiler is there to detect.

Paging one 400 MiB transformer block costs a D2H and an H2D of 400 MiB, about 30 ms of link time at duplex factor 1. A block's forward takes about 6 ms on this GPU. Hiding a block's paging behind compute would take roughly 67 GB/s, so beyond a small prefix, paging activations here is a memory-for-time trade, not free. TrainStream makes the trade explicit (see tuning).

Beginner phase

Why GPUs run out of memory

Training a model needs far more memory than storing it. With the Adam family of optimizers, every single parameter brings along:

  • the weight itself (4 bytes in fp32),
  • its gradient (4 bytes, rewritten every step),
  • two running averages that Adam keeps, the first and second moments (4 + 4 bytes).

That's 16 bytes per parameter before a single activation is stored, so a 1.5B-parameter model needs 24 GB just for this bookkeeping. On top of that, the forward pass saves activations (intermediate results) so the backward pass can use them, and they grow with batch size and sequence length.

What actually has to be on the GPU

Only the data the GPU is computing with right now: the weights, plus one or two blocks' worth of activations and gradients. The optimizer moments are only touched once per step, by simple element-wise math, which a CPU does well.

What the host has plenty of

A workstation or laptop often has 2–8× more system RAM than VRAM, and a PCIe link that moves roughly 25–60 GB/s. TrainStream's job is to move the right bytes across that link at the right moment, while the GPU keeps working.

About the C++ standard

TrainStream's own sources use only C++17 features, and the CUDA translation unit includes nothing but CUDA headers. Recent PyTorch headers (2.10+) require C++20, so files that include ATen are compiled in C++20 mode; torch.utils.cpp_extension adds that flag automatically.

Beginner phase

Your first fine-tune

Take any ordinary training loop. The only new line is the call to wrap; everything else stays standard PyTorch.

finetune.py
import torch
import trainstream

model = MyTransformer().cuda()                       # weights must already be on the GPU
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4, weight_decay=0.1)

model, optimizer = trainstream.wrap(model, optimizer)   # moments -> host, hooks installed

scheduler = torch.optim.lr_scheduler.CosineAnnealingLR(optimizer, T_max=10_000)  # create AFTER wrap

for x, y in loader:
    with torch.autocast("cuda", dtype=torch.bfloat16):
        loss = model(x.cuda(), y.cuda())
    loss.backward()            # gradients stream to host RAM as they are produced
    optimizer.step()           # returns immediately; updates finish in the background
    optimizer.zero_grad()
    scheduler.step()

optimizer.synchronize()        # wait for the last update before saving
torch.save({"model": model.state_dict(), "optim": optimizer.state_dict()}, "ckpt.pt")

Gradient accumulation and clipping

Because gradients leave the GPU during backward, torch.nn.utils.clip_grad_norm_ has nothing to see. Pass clipping and accumulation to wrap instead:

python
model, optimizer = trainstream.wrap(
    model, optimizer,
    accumulation_steps=4,      # backward passes per optimizer.step()
    max_grad_norm=1.0,         # global-norm clipping, computed on the host
)

Declare your accumulation

With accumulation_steps=1 (the default) and no clipping, each tensor's update runs during backward. If you run a second backward before step() without declaring it, TrainStream raises an error instead of silently changing your training math.

Beginner phase

Key terminology

VRAM
The GPU's own memory. Fast and scarce: everything the GPU computes on must be here.
Host RAM
Your computer's main memory. Larger and slower to reach from the GPU.
PCIe
The bus connecting GPU and CPU. Every offloaded byte crosses it, at tens of GB/s.
Pinned memory
Host RAM locked so the OS can't move it. The GPU's copy engines can then DMA into it directly and asynchronously, at about twice the speed of ordinary (pageable) memory here.
DMA
Direct memory access: a hardware copy engine moves data while the GPU's compute units keep working.
CUDA stream
A queue of GPU work that runs in order. Work on different streams can overlap.
CUDA event
A marker recorded into a stream. Another stream can wait on it, giving ordering without stopping the CPU.
Activations
Intermediate results saved during forward because backward needs them.
Optimizer state / moments
Adam's per-parameter running averages of the gradient (m) and squared gradient (v).
Master weights
An fp32 copy of the weights used for the update when the GPU weights are fp16/bf16.
Prefetch
Starting a transfer before the data is needed, so it has arrived by the time it is.
Zero-copy
A GPU kernel reads and writes host memory directly over PCIe, without a separate copy step.

Intermediate phase

Double-buffered stream prefetching

The activation pager plugs into torch.autograd.graph.saved_tensors_hooks. Everything autograd saves inside a selected block goes through pack during forward and comes back through unpack during backward.

Forward: pack

  1. Skip parameters, non-CUDA tensors and anything smaller than min_offload_bytes. Those come back as a light _Resident tag that still knows its block, so unpacking it can trigger the next prefetch.
  2. Deduplicate. Several ops often save the same tensor (q, k and v projections all save the LayerNorm output). A weak-reference map ensures each tensor is copied once.
  3. Allocate a pinned stash from the caching allocator, queue d2h_async (the copy stream waits on an event recorded on compute), and keep the VRAM source alive only until that copy's event completes.
  4. Backpressure. If more than max_inflight_bytes are still crossing the link, the host waits for the oldest copy. Without this, a fast GPU outruns PCIe and paging saves almost no memory: on the 1.8B model, 43% paging saved 0.4 GiB without backpressure and 3.9 GiB with it.

Backward: unpack

  1. On the first touch of block b, stage blocks b−1 … b−depth with h2d_alloc_async. The destination comes from the compute stream's own pool, so paging never splits VRAM into a second per-stream pool, and the copy is ordered after work already queued there.
  2. Return the tensor after making the compute stream wait (GPU-side) on its H2D event. The host never blocks.
  3. The tensor is restored with its exact original strides; see pitfalls for why that matters.

from trainstream import ActivationOffloader, find_blocks

off = ActivationOffloader(model, find_blocks(model), offload=0.5,   # first 50% of blocks
                          prefetch_depth=1, min_bytes=1 << 20, max_inflight_bytes=1 << 30)
...

Intermediate phase

Offloaded AdamW mechanics

Both optimizer modes reproduce torch.optim.AdamW's arithmetic order exactly: decoupled decay, lerp for m, addcmul for v, and denom = √v / √(1−β₂ᵗ) + ε. That's why parity comes out at about 3e-7 rather than "close enough".

cpu mode: host AdamW

Each parameter becomes a slot split into 1M-element chunks. Chunk c of slot s always goes to worker (s·2654435761 + c) mod T, so accumulate → norm → update for any chunk run in FIFO order on one thread without locks. When the last chunk of a slot finishes, its finaliser queues the H2D upload on the h2d stream and publishes the slot's ready event.

csrc/offload_adamw.cpp · inner loop
template <typename G, typename P, bool kStage>
void adamw_host(float* p, float* m, float* v, const G* g, P* stage,
                int64_t b, int64_t e, const HostHp& hp) {
  const float decay = 1.0f - hp.lr * hp.weight_decay;
  for (int64_t i = b; i < e; ++i) {
    const float gi = static_cast<float>(g[i]) * hp.clip;     // fp32 accumulator or raw DMA staging
    const float mi = m[i] + (1.0f - hp.beta1) * (gi - m[i]);  // lerp
    const float vi = hp.beta2 * v[i] + (1.0f - hp.beta2) * gi * gi;
    const float pi = p[i] * decay - hp.step_size * (mi / (std::sqrt(vi) / hp.bc2_sqrt + hp.eps));
    m[i] = mi; v[i] = vi; p[i] = pi;
    if constexpr (kStage) stage[i] = static_cast<P>(pi);     // bf16/fp16 copy for the upload
  }
}

Eager updates. With a single micro-batch and no clipping, the update for a tensor is queued from inside its gradient hook, and reads the pinned DMA staging buffer directly, with no fp32 accumulator round trip. On the 85M model this cut the post-backward drain from 42 ms to 19 ms.

gpu mode: zero-copy kernel

Moments are allocated with cudaHostAllocMapped, and the kernel dereferences their device aliases directly. Each warp-wide load becomes a PCIe read, so the kernel is bus-bound by design (16 B of traffic per fp32 parameter). It hides about 1–2 µs of PCIe latency by issuing every load for four unrolled elements before consuming any of them:

csrc/offload_adamw_kernel.cu
#pragma unroll
for (int u = 0; u < kUnroll; ++u) {             // phase 1: put 4 × 3 host reads in flight
  const int64_t i = base + u * kThreads;
  if (i < n) { g[u] = Cvt<T>::load(grad[i]) * clip; m[u] = exp_avg[i]; v[u] = exp_avg_sq[i];
               p[u] = master ? master[i] : Cvt<T>::load(param[i]); }
}
#pragma unroll
for (int u = 0; u < kUnroll; ++u) { /* phase 2: AdamW math, posted PCIe writes */ }

Intermediate phase

PyTorch backward hooks

wrap() installs three kinds of hooks, all removable with trainstream.unwrap(model):

HookWhereJob
register_post_accumulate_grad_hookevery parameterFires after autograd has finished accumulating into .grad, including tied weights used twice. Queues the D2H (plus the eager update) and sets param.grad = None to free VRAM.
register_forward_pre_hookevery module that owns parametersWaits until that module's own updates have been issued, then makes compute wait (GPU-side) for them to land. Also records first-forward order, so updates run front-to-back.
saved_tensors_hooks (+ block pre/post hooks)root module and the block stackActivation paging, block timing during calibration, and the step clock for the auto tuner.
trainstream/hooks.py · the gradient hook
def hook(param):
    grad = param.grad
    if grad is None:
        return
    on_grad(slot, grad)      # D2H on the copy stream (+ eager AdamW when this is the last micro-batch)
    param.grad = None        # VRAM released; the engine holds the tensor until the DMA has landed

Why a post-accumulate hook rather than a tensor hook: a tensor hook sees each contribution to a gradient, while the post-accumulate hook sees the final sum, which is the only safe moment to stream it out.

Intermediate phase

Profile-driven tuning

With activation_offload="auto" (the default), the pager runs a closed loop instead of trusting a formula:

  1. Calibrate (3 steps, nothing paged): measure per-block saved bytes, per-block forward time with CUDA timing events, and wall-clock step time.
  2. Predict the paged prefix K from the link model. The optimizer's own traffic is reserved first, and the duplex factor decides whether D2H and H2D add up or overlap:
    trainstream/profiler.py
    link_ms(d2h, h2d) = max(t_d2h, t_h2d, (t_d2h + t_h2d) / duplex_factor)
K = (step_ms * 0.85 - reserved_link_ms) / link_ms(block_bytes, block_bytes)
  3. Tune: measure the real step time with K blocks paged, and halve K until the slowdown is within max_activation_slowdown (15% by default) of the calibrated baseline.

On the 85M model, prediction chose 3 of 12 blocks and tuning settled on 1. When memory matters more than speed, pin the fraction instead, for example activation_offload=1.0.

Intermediate phase

Prove it: is training memory really in system RAM?

"It didn't crash" isn't proof. Two different things can put training data in system RAM, and only one of them is TrainStream:

TrainStream (intentional, fast)

Optimizer state, gradients and paged activations in pinned host buffers, moved by DMA on dedicated streams at about 28 GB/s. This happens by design, from the first step, not only once VRAM is full.

The Windows driver (silent, slow)

When a process overflows VRAM, WDDM's "sysmem fallback" quietly backs GPU allocations with system RAM. Nothing crashes, but every kernel touching those pages slows down. Stock AdamW on the 1.8B model spilled 13.85 GiB this way.

The Task Manager trap

Windows reports CUDA pinned host memory under "Shared GPU memory", the same counter that rises during a driver spill. A test allocation of exactly 4 GiB pinned showed up as 4,172 MiB of shared usage. So high shared GPU memory alone doesn't mean anything went wrong. Subtract TrainStream's pinned bytes; whatever is left over is spill.

The automated proof

Advanced phase

Custom stream synchronization with CUDA events

TrainStream never calls cudaDeviceSynchronize on the hot path. Every cross-stream dependency is an event, recorded by the producer and waited on by the consumer's stream. Events come from a per-device recycling pool, so thousands per step cost almost nothing. Re-recording a pooled event is safe because cudaStreamWaitEvent snapshots the event's state when it's called.

csrc/memory_pinner.cpp · d2h_async
EventPtr d2h_async(const at::Tensor& dst, const at::Tensor& src) {
  Runtime& rt = runtime(src.get_device());
  auto produced = make_event(dev);
  produced->record(compute_stream(dev));   // everything that writes src is queued before this
  produced->block(rt.d2h);                  // cudaStreamWaitEvent: the copy waits, the host does not
  cudaMemcpyAsync(dst.data_ptr(), src.data_ptr(), src.nbytes(), cudaMemcpyDeviceToHost, rt.d2h);
  auto done = make_event(dev);
  done->record(rt.d2h);                     // consumers wait on (or poll) this
  return done;
}

Two kinds of wait, used deliberately

WaitBlocksUsed for
Event.wait() → cudaStreamWaitEventonly the GPU streamcompute waiting for weights and prefetches; copy streams waiting for producers
Event.synchronize() → cudaEventSynchronizethe calling host threada worker waiting for gradient bytes to land before reading them; backpressure
condition variable on slot inflighthost, until an update is issuedmodule pre-hooks: an event can't be waited on before it has been recorded

The "issued vs landed" subtlety

Waiting on an event that hasn't been recorded yet is a silent no-op in CUDA. The forward pre-hook therefore first waits (host-side, GIL released) for the worker to have queued the upload, and only then calls cudaStreamWaitEvent. Skipping the first step causes nondeterministic stale-weight reads.

Stream priorities matter too. H2D is created at the device's highest priority because prefetches sit on backward's critical path; D2H and the zero-copy stream run at the lowest.

Advanced phase

Custom host memory allocators via the PyTorch C++ API

cudaHostAlloc is slow (it page-locks memory in the kernel), and activation stashes churn every step, so TrainStream keeps a size-bucketed cache in front of it. Blocks are wrapped as ordinary ATen tensors with at::from_blob and a custom deleter, so they behave like any other tensor in Python.

csrc/memory_pinner.cpp
at::Tensor pinned_empty(const std::vector<int64_t>& sizes, at::ScalarType dtype,
                        const std::string& tag, bool mapped, bool cached) {
  at::globalContext().lazyInitDevice(at::kCUDA);   // else Tensor.is_pinned() reports false
  void* ptr = PinnedAllocator::get().allocate(nbytes, mapped, cached, tag);
  return at::from_blob(ptr, sizes,
                       [](void* p) { PinnedAllocator::get().release(p); },   // back to the cache
                       at::TensorOptions().dtype(dtype).device(at::kCPU));
}
  • Buckets: 4 KiB granularity below 1 MiB, 2 MiB above. A cached block is reused if it wastes at most 25% (or one 2 MiB page).
  • Event-fenced reuse: on release, a fence event is recorded on each copy stream, and the block re-enters the free list only after all fences pass. If a fence can't be created (for example, the device is out of memory), the streams are drained instead. A block is never recycled unfenced.
  • Pin logging: every alloc, hit, release and free goes into a 4,096-entry ring buffer, with live bytes tracked per tag (adamw.master_fp32, grad.staging, activations, …). trainstream.pinned_stats() and the dashboard's pinned-memory panel read it.
  • Budget: page-locking too much RAM makes the OS fail DMA mappings, which on this machine surfaced as asynchronous CUDA out-of-memory errors above about 40 GB pinned. Moments are therefore pinned only within 40% of physical RAM (pin_moments overrides this). In cpu mode only host threads touch them, so pinning them isn't required for correctness.
Advanced phase

PCIe DMA transaction tuning

Transfer size

Bandwidth reaches 94% of peak at 1 MiB here, and only 19% at 64 KiB. Keep individual DMAs at 1 MiB or larger: page per tensor, not per row, and leave small tensors resident.

Pinned or pageable

Pageable memory forces the driver to bounce through its own staging buffer (14.5 vs 27.9 GB/s here) and makes cudaMemcpyAsync effectively synchronous. Every buffer that is a DMA endpoint is pinned.

Direction mix

Measure the duplex factor; don't assume it. At 1.0, gradient D2H and prefetch H2D compete during backward, so reserve link time for the optimizer first.

Zero-copy access patterns

Mapped memory works only with coalesced, streaming access. Each warp issues 128-byte requests, and the 4-way load-first unroll keeps about 12 reads per thread in flight to cover latency.

Advanced phase

Correctness pitfalls we hit (and the tests that pin them down)

Saved-tensor layout must survive the round trip

An early pager restored every activation as contiguous. Under bf16, SDPA picks the memory-efficient attention kernel, whose backward silently returns wrong gradients when its saved q/k/v/out come back with a different stride order. The isolated reproducer showed a max gradient error of 54.75, and at 300M parameters training went to NaN. The fix copies dense tensors byte-for-byte and restores their exact strides; non-dense views (q/k/v sliced from a fused qkv) are packed densely in their original dimension order. test_activation_offload_preserves_layout_for_fused_attention checks bit-exact gradients on the efficient, cuDNN and math backends.

recordStream can abort the process on a full device

Tagging blocks with recordStream for the copy streams makes PyTorch's caching allocator create CUDA events inside its free path. On a nearly full card that event creation failed inside a destructor, and std::terminate killed the process. TrainStream now keeps explicit lifetimes instead: D2H sources are held until their copy event completes, prefetch buffers come from the consumer's pool and are waited on before use or release, and streamed gradients are released by the worker once the host has consumed them. A terminate hook in the extension prints the real message ([trainstream] terminate: …) rather than a bare stack trace.

A reference cycle leaked a step of pinned activations each step

Handles pointed to their forward session and the session listed its handles, so buffers waited for Python's cyclic garbage collector, adding about 5.9 GB of pinned memory per step on the 1.8B model. Sessions now hold only weak references, so the autograd graph owns the buffers. test_paged_activations_are_freed_every_step runs with the GC disabled.

Eager updates and step() raced

A slot's has_grad flag was cleared by the asynchronous finaliser, so a step() issued before it ran could update the slot a second time. It's now cleared synchronously when the eager update is queued. Five consecutive full-suite runs pass, and parity tests cover the attached, eager and accumulation paths.

bf16 attention backward isn't deterministic anyway

When comparing paged and unpaged gradients under autocast, two runs without any paging already differ by 1.95e-3, the same amount as paged versus unpaged. Parity tests therefore compare in fp32, or fix the attention backend, where TrainStream is bit-exact.

Advanced phase

Extending the engine to multi-GPU pipeline parallelism

Status: design guide

The runtime is already per-device: streams, event pools and transfer counters are keyed by device index, and an OffloadAdamW engine binds to one device. The pipeline scheduling below is a worked design, not shipped or tested code.

  1. One engine per stage. Place stage i's blocks on cuda:i and give each stage its own OffloadAdamW and ActivationOffloader. Each stage then streams over its own PCIe lanes.
    python · sketch
    stages = [nn.Sequential(*blocks[a:b]).to(f"cuda:{i}") for i, (a, b) in enumerate(splits)]
opts = [trainstream.OffloadAdamW(s.parameters(), lr=3e-4).attach(s) for s in stages]
pagers = [trainstream.ActivationOffloader(s, list(s), offload="auto",
                                          profile=trainstream.profile_hardware(f"cuda:{i}"))
          for i, s in enumerate(stages)]
  2. Hand-offs with events, not syncs. Send stage i's output with tensor.to(f"cuda:{i+1}", non_blocking=True) (peer-to-peer where available), recorded behind an event on stage i's compute stream. Stage i+1's stream waits on that event, the same pattern as d2h_async.
  3. 1F1B schedule with paging. In a one-forward-one-backward schedule, stage 0 holds up to P micro-batches of activations, which is where VRAM peaks. Page micro-batches in the order they will be consumed, and set prefetch_depth to the number of micro-batches between a forward and its backward on that stage.
  4. Share the host fairly. All stages draw on one pool of RAM bandwidth for host AdamW (about 75 GB/s here). Split threads across engines, and on multi-socket hosts allocate each stage's pinned buffers on the NUMA node nearest its GPU's root complex.
  5. Profile per link. GPUs behind a shared PCIe switch split its bandwidth; run profile_hardware with all stages active and feed each pager its own profile.

Limitations

  • The output logits of large-vocabulary models are not offloaded. For Qwen (151,936 tokens), batch 4 × 512 tokens of fp32 logits alone is 1.16 GiB, plus their gradient. On small GPUs, reduce the batch size or use a chunked loss.
  • Weights stay resident in VRAM; only optimizer state, gradients and activations are offloaded. A model whose weights alone exceed VRAM needs parameter paging, which isn't implemented.
  • Parameters used outside their owning module's forward (functional calls on another module's weight) bypass the readiness hook. Call optimizer.synchronize() before such reads, or use attach() on that module.
  • Moving a wrapped model with .to() after wrap() invalidates the engine's device pointers. Wrap last.
  • For small models that already fit, cpu mode is slower than fused GPU AdamW; host AdamW is bounded by RAM bandwidth (about 2.6 Gelem/s here).
  • Multi-GPU pipeline parallelism is a documented design, not shipped code.
  • Tested on Windows 11 with an RTX 5090 Laptop GPU (sm_120), CUDA 13.4, PyTorch 2.14.1 and Python 3.14. Linux builds use the same setup.py but haven't been exercised here.
