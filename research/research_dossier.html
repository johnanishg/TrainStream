Draft

Abstract (draft, numbers filled in)

Fine-tuning and training large language models is limited first by GPU memory: with Adam-family optimizers every parameter costs 16 bytes of VRAM in fp32 before a single activation is stored. We present TrainStream, a dependency-free C++/CUDA extension for PyTorch that moves optimizer state, gradients and a profiled fraction of activations to pinned host RAM over PCIe and overlaps the traffic with computation. TrainStream (i) streams each gradient to the host the moment autograd finalizes it and runs that tensor's AdamW update on host threads during the remainder of the backward pass, gating the next forward pass per module on CUDA events rather than host synchronization; (ii) pages saved activations through layout-preserving saved-tensor hooks with a duplex-aware link model, closed-loop tuning and transfer back-pressure; and (iii) manages buffer lifetimes without allocator stream tagging, which we show can abort a process when the GPU is full. On a 24 GB laptop GPU, TrainStream trains a 1.8B-parameter model in fp32 within 20.55 GiB of VRAM (down to 13.51 GiB with full activation paging) where stock AdamW needs 34.06 GiB and silently spills into system memory, and fully fine-tunes Qwen2.5-1.5B with the Hugging Face Trainer in 18.66 GiB instead of 35.92 GiB, 3.9× faster than the spilling baseline, with step-for-step matching losses. Optimizer updates match torch.optim.AdamW to within 3·10⁻⁷ and activation paging is bit-exact. We also report three correctness hazards of offloading in eager frameworks and a measurement methodology that distinguishes intentional pinned host memory from driver-level VRAM oversubscription.

Motivation

Problem statement

For a model with N trainable parameters trained with Adam/AdamW in fp32, the static VRAM requirement before any activation is stored is

MGPUAdamW = N · (bw + bg + 8)  =  16·N bytes (fp32)

so a 1.5B-parameter model needs ≈24 GB for weights, gradients and moments alone — the entire memory of the GPU used here. Activations add a batch- and sequence-dependent term on top. Meanwhile the host offers 2–4× more RAM and a PCIe link that is idle during most of training. The optimizer state is touched once per step by element-wise arithmetic, an ideal candidate for the host; gradients are produced and consumed exactly once per step; activations are produced in forward order and consumed in reverse order, which makes them prefetchable.

Research questions. RQ1: How much VRAM can be released by moving optimizer state, gradients and activations to host RAM in an eager framework, without changing training semantics? RQ2: What does it cost in throughput on a realistic consumer link, and how much can be hidden behind computation? RQ3: Which correctness and stability hazards arise, and how can they be avoided? RQ4: How can one verify, from outside the process, that memory really moved to host RAM rather than being silently oversubscribed by the driver?

Claims

Candidate contributions

  1. Eager, exact host-side AdamW with per-module gating. Each tensor's update is queued from its post-accumulate-grad hook and runs on host threads during the rest of backward; the next forward waits per module on CUDA events. Unlike a one-step delayed update, parameters are never stale, so results match torch.optim.AdamW step for step.
  2. Fused staging read. For single-micro-batch steps the update reads the DMA staging buffer directly, removing the fp32 accumulator round trip (drain 29.1 → 18.8 ms on 85M).
  3. Duplex-aware, closed-loop activation paging with back-pressure. A link model that uses the measured duplex factor and reserves optimizer traffic predicts the paged prefix; real step times then tune it; a bound on bytes in flight turns paging into a guaranteed VRAM reduction rather than a best-effort one.
  4. Correctness findings for offloading in eager frameworks: (a) restoring saved tensors with a different stride order silently corrupts gradients of fused memory-efficient attention; (b) allocator stream tagging (recordStream) can abort the process when VRAM is full; (c) a handle/session reference cycle leaks a step of pinned memory per step.
  5. A verification methodology that proves where training memory lives (allocator accounting, OS commit counters, live tensor inspection, PCIe byte counters) and separates TrainStream's pinned buffers from WDDM's shared-memory spill, which the OS reports under the same counter.
  6. An artifact: a zero-dependency PyTorch extension, a one-line API, a Hugging Face Trainer integration and a one-click comparison harness.

Novelty check before submission

Contribution 1 is closest to ZeRO-Offload's CPU optimizer and its delayed parameter update; contribution 3 relates to swapping systems (vDNN, SwapAdvisor, Capuchin) and ZeRO-Infinity's activation offload. Position the paper on exactness without staleness, closed-loop sizing on consumer links and the hazard/verification findings, and re-read those papers to make sure each claim is differentiated.

Background

Background the paper should cover

AdamW state
Two fp32 moments per parameter (m, v); decoupled weight decay [loshchilov2019adamw]. Updates are element-wise and memory-bandwidth bound.
Mixed precision
bf16 autocast for compute with fp32 master weights [micikevicius2018mixed]; TrainStream keeps the fp32 master on the host when weights are bf16/fp16.
Saved tensors
PyTorch autograd stores tensors needed by backward; saved_tensors_hooks intercept pack/unpack, which is where activation paging happens.
Post-accumulate-grad hook
Fires once a parameter's gradient is final (after all contributions), the earliest safe point to stream and update it.
CUDA streams & events
Independent queues; an event recorded on one stream can be waited on by another without blocking the host.
Pinned vs pageable
Page-locked memory allows asynchronous DMA at full link speed (27.9 vs 14.5 GB/s measured); too much locked memory makes the OS fail DMA mappings.
Mapped (zero-copy) memory
Pinned memory addressable from kernels; every access becomes a PCIe transaction.
WDDM sysmem fallback
On Windows the driver may back GPU allocations with system RAM when VRAM is exhausted ("shared GPU memory"): no OOM, but a large slowdown.
System

Design

6.1 Data paths

Optimizer state and gradients (cpu mode). In the post-accumulate-grad hook of parameter p, a D2H copy of the gradient into a pinned staging buffer is queued on the D2H stream after an event recorded on the compute stream. The VRAM gradient is released as soon as the host has consumed it. Host worker threads accumulate (when micro-batching) and run AdamW on the fp32 master and moments, then queue an H2D copy of the new weights (or a rounded bf16/fp16 copy) on the H2D stream, ordered after an event recorded when the gradient was produced. A per-slot ready event is published.

Per-module readiness. A forward pre-hook on every module that owns parameters waits (host side, GIL released) until the module's updates have been issued and then makes the compute stream wait on their ready events (GPU side). The issued/landed split matters: waiting on an event that has not been recorded yet is a silent no-op in CUDA.

Zero-copy mode (gpu). Gradients stay in VRAM until step(); a fused kernel updates weights in place while reading and writing the moments through mapped pinned memory. It issues all loads of a four-way unrolled body before any arithmetic to keep ≈12 PCIe reads per thread in flight. Moments never occupy VRAM.

Activations. Saved tensors produced inside selected transformer blocks are copied D2H into pinned stashes during forward (deduplicated by tensor identity) and staged back H2D on the high-priority stream when backward first touches the block above them (a ping-pong window of depth k, default 1).

6.2 Eager update algorithm

on post_accumulate_grad(p):                        # autograd thread
    micro[p] += 1
    wait until slot(p) has no in-flight work        # staging buffer reuse
    e_prod ← record(compute); copy_stream.wait(e_prod)
    D2H(grad(p) → stage[p]) on d2h;  e_d2h ← record(d2h)
    if eager and micro[p] = A (accumulation steps) and no clipping:
        enqueue AdamW(p, reads stage[p] after e_d2h)    # fused staging read
        then H2D(master[p] → p) after e_prod;  ready[p] ← record(h2d)
    else: enqueue accumulate(stage[p] → acc[p])
    grad(p) ← None                                   # VRAM released when the D2H has landed

on forward_pre(module):
    for p in params(module): wait until update(p) issued;  compute.wait(ready[p])

on step():   (non-eager path) record e_step; enqueue remaining updates in first-forward order

Chunks of 1M elements are assigned to worker (s·φ + c) mod T, which gives per-chunk FIFO ordering of accumulate → norm → update without locks. Global-norm clipping requires all gradients, so it disables the eager path and uses a host reduction barrier inside step().

6.3 Lifetime management without allocator stream tagging

The standard way to use a tensor on a side stream is recordStream, which makes the caching allocator record events when the tensor is freed. We found that this event creation can fail inside a destructor when the device is full, which terminates the process (§10). TrainStream instead keeps explicit lifetimes: D2H sources are held until their copy event completes (polled, with back-pressure), prefetch buffers are allocated from the consumer stream's pool with the H2D ordered after an event on that stream and are waited on before use or release, and streamed gradients are released by the worker after the host has consumed them.

6.4 Pinned memory

A pin-logging caching allocator wraps cudaHostAlloc: size buckets (4 KiB below 1 MiB, 2 MiB above), event-fenced reuse (a released block re-enters the free list only after fences on every copy stream pass; if fences cannot be created the streams are drained), per-tag accounting and a ring log. Moments are pinned only while the total stays within 40 % of physical RAM; the fp32 master and staging buffers (the DMA endpoints) are always pinned.

Model

Analytical model

Memory per parameter

PCIe traffic per step

cpu mode:   D2H = N·bg,   H2D = N·bw   |   zero-copy: 16·N (+8·N with a host fp32 master)   |   activations: 2·Sblk per paged block

Link model and activation sizing

κ = Bbidir / max(BH2D, BD2H) ∈ [1, 2]     link(d, h) = max( d/BD2H, h/BH2D, (d/BD2H + h/BH2D) / κ )
K = ⌊ (s · Tstep − link(N·bg, N·bw)) / link(Sblk, Sblk) ⌋,   s = 0.85    → page blocks 0 … K−1

Tstep is the measured un-paged step time from calibration (three steps). The tuner then measures real step time with K blocks paged and halves K while TK > (1 + ε)·T0 (ε = 0.15 by default). Back-pressure bounds the bytes of sources still crossing the link by β (1 GiB): beyond it, the host waits on the oldest copy.

Break-even arithmetic intensity

I* = Fbf16 / BH2D = 94.6·10¹² / 27.9·10⁹ ≈ 3,391 FLOP/byte

A transfer is hideable behind matmuls only if the work it enables exceeds I* FLOPs per byte moved. A transformer block's activations (≈400 MiB at d=2048, batch 8×512) take ≈30 ms of link time at κ = 1, while the block's forward takes ≈6 ms on this GPU — so beyond a short prefix, paging trades time for memory (measured in R4).

Host update bound

Host AdamW reads p, m, v, g and writes p, m, v (≈28 B/element plus staging); at the measured 2.54–2.81 G elem/s this is ≈70–78 GB/s, i.e. DRAM-bandwidth bound. For N parameters the host needs ≈N / Rhost per step (≈0.7 s for 1.8B), which eager updates overlap with backward.

Metrics and how they are measured

  • Peak VRAM: torch.cuda.max_memory_allocated per step (allocator view); device-wide usage from cudaMemGetInfo.
  • Host memory: engine accounting (pinned + pageable state), process committed memory (GetProcessMemoryInfo.PrivateUsage), system available RAM.
  • Driver spill: Windows performance counters GPU Process Memory\Dedicated Usage and \Shared Usage per process, minus TrainStream's own pinned bytes (which Windows also reports as shared).
  • Traffic: bytes issued on TrainStream's D2H/H2D streams per step.
  • Time: wall time between successive loss values (synchronising only the compute stream) or, in probes, with explicit synchronisation per phase.
  • Correctness: max |Δ| of parameters/gradients vs reference; loss trajectories.

Protocol

Each engine runs in a fresh state (separate process in the verification tool; cache release between engines in the dashboard). Stock runs are stopped when device VRAM exceeds 95 % (to avoid multi-minute spills) unless spilling is the object of study, and all runs stop if free system RAM falls below 3 GiB. Single runs, no repetitions yet — see threats.

Measurement pitfall worth a paragraph in the paper

Windows reports CUDA pinned host memory as "Shared GPU memory": allocating exactly 4 GiB of pinned memory raised the process's shared-usage counter by 4,172 MiB, while 4 GiB of VRAM raised dedicated usage by 4,382 MiB. The same counter is what grows during a driver spill. Subtracting TrainStream's own pinned bytes leaves 0.08–0.09 GiB unexplained, versus 13.85 GiB of genuine spill in the positive control (GPT 1.8B, stock AdamW, no cap, batch 4: peak 28.92 GiB on a 23.89 GiB card, 21.32 GiB dedicated + 13.85 GiB shared).

Interpretation. When the model fits, TrainStream costs throughput: host AdamW is bounded by DRAM bandwidth and the link is shared by gradients, weights and activations. The benefit is capacity: workloads that do not fit (or fit only by spilling) become trainable, and VRAM freed on smaller models can be spent on larger batches. Pinned-memory budget

Pinning all optimizer state of the 1.8B model (33.8 GiB) plus activation stashes led to asynchronous CUDA out-of-memory errors at ≈39.7 GB of page-locked memory on a 63 GB machine. Limiting pinning to 40 % of RAM moved the moments to pageable memory (13.5 GiB pinned + 13.5 GiB pageable) with no change in results, because only host threads touch the moments.

Positioning

Related work and how TrainStream differs

  • ZeRO family [rajbhandari2020zero; ren2021zerooffload; rajbhandari2021zeroinfinity] partitions and offloads optimizer state, gradients and (ZeRO-Infinity) parameters and activation checkpoints to CPU/NVMe; ZeRO-Offload runs a vectorised CPU Adam and offers a one-step delayed parameter update to overlap it. TrainStream targets a single consumer GPU, keeps updates exact (no delay) by gating per module, sizes activation paging from measured link behaviour, and is a single-library drop-in for PyTorch eager.
  • Swapping and recomputation: vDNN [rhu2016vdnn], SwapAdvisor [huang2020swapadvisor], Capuchin [peng2020capuchin], gradient checkpointing [chen2016checkpointing]. TrainStream's pager is a runtime hook-based instance of swapping with a closed loop instead of a static plan; combining it with checkpointing is future work.
  • Reducing state instead of moving it: 8-bit optimizers [dettmers2022eightbit], LoRA [hu2022lora], QLoRA [dettmers2023qlora] are orthogonal and composable (LoRA support is evaluated).
  • Attention memory: FlashAttention [dao2022flashattention] and memory-efficient attention [rabe2021selfattention] — relevant both as activation-memory reducers and as the source of the layout hazard.
  • Inference offloading: FlexGen [sheng2023flexgen] schedules weights/KV cache over a GPU-CPU-disk hierarchy for throughput; TrainStream addresses training.
  • Frameworks: PyTorch [paszke2019pytorch], FSDP with CPU offload [zhao2023fsdp], Hugging Face Transformers [wolf2020transformers].

Honesty

Limitations

  • Weights stay resident: a model whose weights alone exceed VRAM cannot be trained (no parameter paging).
  • Output logits of large-vocabulary models are not offloaded (Qwen, batch 4×512: 1.16 GiB of fp32 logits plus gradient).
  • Host AdamW relies on compiler auto-vectorisation and is DRAM-bandwidth bound (2.5–2.8 G elem/s); explicit SIMD (as in ZeRO-Offload's CPU Adam) would help.
  • Single GPU per process; the multi-GPU pipeline design is documented, not implemented.
  • fp16 with loss scaling is unsupported (GradScaler needs gradients on the GPU); bf16 and fp32 are supported.
  • All measurements come from one Windows laptop with a duplex factor of 1.0; results on full-duplex Linux systems will differ (likely favourably for paging).
  • The TensorFlow reference runs on DirectML (no CUDA support for this GPU in Windows TensorFlow); it reserved ≈19 GB of RAM and ≈10 GiB of GPU memory even for 85M parameters and varied 36× in speed between identical runs, so it is not a fair baseline.
Validity

Threats to validity

  • Internal: single runs; bf16 nondeterminism (≈2·10⁻³ gradient noise); stock baselines stopped at 95 % VRAM rather than run to completion; first steps include allocator warm-up (excluded via medians).
  • External: one machine, one OS (WDDM), one GPU generation, a byte-level corpus; Hugging Face results on one model family.
  • Construct: "peak VRAM" is the allocator's view; device usage includes the CUDA context and other processes; host memory includes pinned caches.
  • Conclusion: speed-ups against a spilling baseline depend on how badly the driver spills (12× at batch 8, smaller at batch 4); report capacity results as primary and speed as secondary.
